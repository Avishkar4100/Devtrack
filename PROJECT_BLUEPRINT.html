AI Powered DevTrack - Complete Project Blueprint

This document captures the full architecture of the project as implemented till now: UI flow, frontend state/actions, backend orchestration, AI service behavior, persistence layer, and Jira publishing pipeline.

Scope: Frontend (React + Vite), Backend (Node/Express + MongoDB), AI Service (FastAPI + LLM + Chroma), Jira integration.

1) High-Level Architecture

Frontend Layer

React SPA with route-based pages, persisted client state, toast + notification history, and API interaction through shared client utilities.

React Vite Zustand (persist) React Query

Backend Layer

Express API that handles auth, projects, documents, stories, insights, Jira bridge, and delegates AI operations to FastAPI service.

Node.js Express Mongoose Winston Logger

AI Service Layer

FastAPI service for extraction/suggest/generate using LLM prompts, context building, and document retrieval support via embeddings/chroma.

FastAPI LLM Service Embeddings Chroma Vector Store

External Integrations

Jira push pipeline and GitHub/Jira analytics connectors from backend controllers and routes.

Jira REST APIs GitHub APIs

2) End-to-End Execution Flow (SRS to Jira)

UI (Upload SRS) -> Backend /documents upload endpoint -> Store document metadata + file -> Trigger ingestion -> AI Service parses chunks + embeddings + vector store write -> Backend marks ingestion status -> AI Service requirement extraction endpoint -> Backend upserts Requirement records UI (AI Planner Suggest) -> Backend /stories/suggest/:projectId -> Build phase-aware context (Requirements + existing stories + commits) -> Call AI Service /stories/suggest -> Validate + strict filtering (remove generic/non-actionable) -> Return suggestions or explicit error (no static fallback) UI (Generate Backlog) -> Backend /stories/generate/:projectId (long running, no forced timeout) -> Call AI Service /stories/generate -> LLM returns hierarchical backlog JSON -> Normalize hierarchy + defaults -> Return generated backlog to frontend UI (Backlog Editor) -> User edits hierarchy (epic/story/task/subtask), assignees, dates, dependencies -> Backend /stories/save/:projectId -> Normalize fields + parent mapping + default status/dates -> Persist stories UI (Push to Jira) -> Backend /jira/push/:projectId -> Create epics, then stories/tasks/subtasks in order -> Map local IDs <-> Jira keys -> Save audit / update results

Frontend Runtime Behavior

  • User uploads document and polls ingestion status through backend APIs.
  • Planner builds prompt context from current project/module/phase inputs and sends suggest call.
  • Generated backlog transitions to dedicated editor route for structured refinement before save/push.
  • State and notifications persist across refresh/session until explicit clear or logout.

Important Backend Behaviors

  • No static suggest fallback: if AI output is empty/unusable, backend returns explicit error.
  • Generation timeout relaxed: long-running generation is allowed to complete.
  • Hierarchy normalization: save path applies defaults for status/dates and parent compatibility.
  • Requirement extraction: ingestion feeds a project-level requirement memory for stronger AI context.

6.2 Common Request Parameters Before AI Calls

Parameter Used In Purpose

requirements[] Suggest, Generate Hard context extracted from SRS; primary grounding source.
existingStories[] Suggest, Generate Prevents duplication and keeps continuity with existing backlog.
recentCommits[] Suggest Adds implementation progress context and technical signals.
constraints Suggest, Generate Rules like "no generic output", "actionable only", "strict JSON".

6.3 Main Prompt Templates (Logical Form)

Below are the logical template shapes used in the AI service. They are intentionally shown as readable blueprint templates.

A) Requirement Extraction Template

SYSTEM ROLE: You are a requirements analyst. Extract concrete, testable requirements from SRS text. INPUT CONTEXT: - Project: {project_name} - Raw SRS chunks: {document_chunks} RULES: - Do not invent requirements. - Group by module and phase where possible. - Keep statements specific and implementation-relevant. - Return strict JSON only. OUTPUT JSON: { "requirements": [ { "module": "...", "phase": "...", "requirement": "...", "priority": "high|medium|low" } ] }

B) Suggest Template (Phase-Aware Actions)

SYSTEM ROLE: You are an engineering planning assistant. Suggest next actionable work items. INPUT CONTEXT: - Module: {module} - Current phase: {phase} - Requirements: {requirements} - Existing stories: {existing_stories} - Recent commits: {recent_commits} RULES: - Suggestions must be phase-appropriate and technically actionable. - Avoid generic placeholders like "improve" or "optimize" without concrete scope. - Prefer tasks that map to verifiable outcomes. - Return strict JSON array. OUTPUT JSON: { "suggestions": [ { "title": "...", "description": "...", "type": "story|task|bug|spike", "phase": "...", "module": "...", "acceptanceCriteria": ["...", "..."] } ] }

C) Generate Template (Jira-Style Hierarchy)

SYSTEM ROLE: You are a Jira backlog architect. Produce a complete hierarchy. INPUT CONTEXT: - Module: {module} - Phase: {phase} - Requirement set: {requirements} - Existing backlog context: {existing_stories} RULES: - Build hierarchy: Epic -> Story -> Task/Subtask. - Every child must map to a valid parent. - Titles and descriptions must be implementation-specific. - Include estimates/priority/dependencies when inferable. - Return strict JSON only. OUTPUT JSON: { "epics": [ { "tempId": "E1", "title": "...", "description": "...", "stories": [ { "tempId": "S1", "parentTempId": "E1", "title": "...", "tasks": [ { "tempId": "T1", "parentTempId": "S1", "title": "..." } ] } ] } ] }

6.4 Parameterized Prompt Assembly Notes

  • Backend composes context from MongoDB (requirements/stories/commits) before calling AI service.
  • AI service inserts normalized context fields into prompt templates and enforces strict JSON responses.
  • Backend validates and filters AI output, then surfaces explicit errors on invalid/empty output.
  • Generation flow keeps long-running calls open and then normalizes hierarchy defaults before returning.

9) Reliability and Quality Controls Added

State Persistence

Project/planner/workspace drafts survive refresh and context switches; cleared on logout for safety.

Notification Memory

Toast history is preserved in bell notifications with seen/unseen controls and stable popup behavior.

AI Failure Transparency

Failures are surfaced to UI instead of masked with generic fallback data.

Structured Suggest Context

Requirements + commits + existing stories + phase/module constraints improve relevance.

Strict Output Filtering

Generic/non-actionable items are filtered before suggestions are accepted by UI.

Long-Running Generate

Generate calls are allowed to run without short client/server timeout cutoffs.
